# รายงานเปรียบเทียบระบบตัวอย่างและข้อมูลรหัสงบประมาณ

วันที่ทบทวน 18 พฤศจิกายน 2569 · ตรวจสถานะโค้ดถึง commit `a7bf37e`

## สรุปผล

HR Budget มีหน้ารายงานรหัสงบประมาณใน Vue และผลตรวจก่อนบันทึกจากตัวนำเข้า Excel ผ่าน `--dry-run` แล้ว งานแรกคือทดสอบหน้าในเบราว์เซอร์ ยืนยันปีเริ่มต้นและขอบเขตข้อมูล แล้วตรวจชุด build สำหรับใช้งานจริง การทบทวนนี้ใช้สองปีเป็นตัวอย่าง ได้แก่ **ไฟล์ Excel ปี 2569 เท่านั้น** และ **คู่มือ PDF ปี 2570** ชุดที่ตรวจยังไม่มีไฟล์ Excel รหัสปี 2570 รายงาน API สามแบบคืนจำนวนรายการ ส่วนรายงานตามประเภทรายจ่ายคืนยอดจัดสรรด้วย

## ขอบเขตการทบทวน

ตรวจระบบตัวอย่าง 7 ไฟล์ใน `secrets/examples/` และข้อมูลรหัสงบประมาณ 3 ไฟล์ใน `secrets/fisical-code/` เทียบกับ PHP API, migrations, ตัวนำเข้า และ Vue SPA ของ HR Budget

## ข้อมูลรหัสงบประมาณ 3 ไฟล์

| ไฟล์ | ผลตรวจ |
|---|---|
| `16002_รหัสงบประมาณ.xlsx` | ชีต `16002` มี 90 รหัสของหน่วยงานเดียว ทุกแถวระบุ ค.ศ. 2026 หรือ พ.ศ. 2569 มีรหัสแม่ 13 หลัก 15 รหัส และรหัสลูก 20 หลัก 75 รหัส ไม่พบรหัสซ้ำ รหัสลูกทั้งหมดจับคู่รหัสแม่ได้จาก 13 หลักแรก |
| `16002_กิจกรรมหลัก.xls` | ชีต `report` มีรหัสกิจกรรมหลัก 17 หลัก 15 รหัส ตัวนำเข้าใช้ปี 2569 ตาม config [Config ตัวนำเข้า](../config/import_fiscal_codes.php#L19) |
| `รหัสงบประมาณ 2570.pdf` | คู่มือสำนักงบประมาณ 4,304 หน้า มีบุ๊กมาร์ก 40 รายการและดึงข้อความได้จากหน้าที่ตรวจ บทกระทรวงยุติธรรมเริ่มที่หน้า PDF 1008 และพบรหัสหน่วยงาน `16002` ที่หน้านี้ ข้อสรุปเดิมว่า PDF เป็นภาพล้วนคลาดเคลื่อน [บันทึกเดิม](../project-log-md/claude-code/handoff-2026-11-16-v2.md#L31) · [วิเคราะห์ภายหลัง](fiscal-code-analysis.md#L15) |

ใช้ Excel ปี 2569 เป็นตัวอย่างข้อมูลสำหรับทดสอบตัวนำเข้า และใช้ PDF ปี 2570 เป็นตัวอย่างอ้างอิงโครงสร้างรหัสอีกปีหนึ่ง คาดว่ารูปแบบและรหัสหลายรายการจะใกล้เคียงกัน แต่ยังไม่ได้วัดความต่างหรือยืนยันว่ารหัสรายตัวใช้ข้ามปีได้ การทดสอบและการอ้างอิงในรายงานนี้จึงระบุปีต้นทางของแต่ละชุด

ตัวนำเข้ารองรับ Excel สองไฟล์ เก็บรหัสงบใน `budget_categories` และรหัสกิจกรรมใน `plans` ส่วนรหัสประเภทรายจ่ายเก็บใน `expense_types` ผ่าน migrations 094–095 migration 095 ยังเพิ่ม `projects.fiscal_code` แม้ตัวนำเข้าไม่ได้เขียนคอลัมน์นี้ [ตัวนำเข้า](../scripts/import_fiscal_codes.php#L189) · [Migration 094](../database/migrations/094_add_fiscal_code_to_expense_types.sql) · [Migration 095](../database/migrations/095_add_fiscal_code_columns.sql)

รหัสลูก 75 รายการแยกตามประเภทรายจ่ายได้ดังนี้ `010` 1 รายการ, `020` 6 รายการ, `031` 9 รายการ, `032` 36 รายการ, `041` 6 รายการ และ `050` 17 รายการ รหัสกลุ่มนี้เก็บใน `expense_types.fiscal_code` [Migration 094](../database/migrations/094_add_fiscal_code_to_expense_types.sql)

ตัวนำเข้าใช้ปี 2569 จาก config สำหรับ activities และข้ามรหัสกิจกรรมที่มีอยู่โดยค้นจากรหัสอย่างเดียวข้ามทุกปี [การค้นรหัส activities เดิม](../scripts/import_fiscal_codes.php#L240) · [Config](../config/import_fiscal_codes.php#L19)

`budget_categories.fiscal_code` มี `uk_fiscal_code` และ `projects.fiscal_code` ก็มี unique key ชื่อเดียวกัน [Migration 095](../database/migrations/095_add_fiscal_code_columns.sql#L38) · [Migration 095](../database/migrations/095_add_fiscal_code_columns.sql#L73) ดังนั้นโมเดลปัจจุบันเก็บรหัสเดิมซ้ำข้ามปีไม่ได้ ตัวนำเข้าข้ามรหัสงบและรหัสกิจกรรมที่ตรวจพบว่ามีอยู่แล้ว หากต้องการเก็บหลายปีต้องเปลี่ยน schema และตรวจชั้นนำเข้าใหม่ [การข้ามรหัสงบเดิม](../scripts/import_fiscal_codes.php#L213)

## ผลกระทบกับรายงานปัจจุบัน

| API ใต้ `/api/v1/reports/fiscal-codes/` | ค่าที่คืน |
|---|---|
| `by-expense-category` | จำนวนรหัสลูกต่อประเภทรายจ่ายและยอดจัดสรร กรองปีเฉพาะยอดจัดสรรจาก `budget_line_items` |
| `by-activity` | จำนวนแถวแผนต่อรหัสกิจกรรมหลักในปีที่เลือก |
| `by-parent-rollup` | จำนวนรหัสลูกต่อรหัสแม่ ไม่มีตัวกรองปี |
| `by-agency` | จำนวนรหัสลูกต่อหน่วยงานและชื่อจาก `divisions.code` หากจับคู่ได้ ไม่มีตัวกรองปี |

- API ใช้ปีที่ส่งมา ตามด้วยปีปัจจุบันในฐานข้อมูล แล้วจึงใช้ค่า config ซึ่งเป็น 2570 การดูข้อมูลกิจกรรมที่นำเข้าจากชุดนี้จึงควรระบุปี 2569 หากปีปัจจุบันต่างกัน [การเลือกปีของ API](../src/Api/Controllers/FiscalCodeReportController.php#L53)
- API ชุดนี้ตรวจเฉพาะการเข้าสู่ระบบผ่าน `AuthMiddleware::require()` (รองรับ Bearer token และ cookie ของ SPA) แต่ไม่ได้ส่งผู้ใช้เข้าบริการหรือจำกัดตามสายหน่วยงาน [Controller](../src/Api/Controllers/FiscalCodeReportController.php#L40) · [Middleware](../src/Api/Middleware/AuthMiddleware.php#L47)
- ส่วนรายงานการใช้งบส่งผู้ใช้เข้า `AccessScopeResolver` และตอบ 403 หากขอบเขตหน่วยงานไม่ตรง [สิทธิ์รายงานการใช้งบ](../src/Api/Controllers/BudgetExecutionController.php#L29)
- หน้า `/fiscal-code-reports` เรียก API ทั้งสี่รายการ และส่งปีเฉพาะสองรายงานที่รองรับ หน้าใช้ปีเริ่มต้นตามปฏิทินของแอป จึงอาจต่างจากผลเรียก API โดยละปี หากข้อมูลหลักตั้งปีปัจจุบันต่างกัน [หน้ารายงาน Vue](../frontend/src/pages/FiscalCodeReportPage.vue) · [คำขอจาก Vue](../frontend/src/queries/fiscalCodeReports.ts)

migration 096 อยู่ใน commit `84b0c5c` แล้ว เพิ่มรหัส `16002` ให้จับคู่ชื่อสำนักงานปลัดกระทรวงยุติธรรมได้ [Migration 096](../database/migrations/096_seed_fiscal_agency_division.sql) · [Rollback 096](../database/migrations/096_rollback_seed_fiscal_agency_division.sql)

### ข้อมูลและการนำเข้า

- ใช้ Excel ปี 2569 ทดสอบการนำเข้าและความสัมพันธ์รหัสแม่–ลูก ใช้ PDF ปี 2570 อ้างอิงโครงสร้าง เมื่อมี Excel ปี 2570 ให้เทียบรหัสที่เพิ่ม หาย หรือเปลี่ยนชื่อและความสัมพันธ์แม่–ลูก ให้เจ้าของข้อมูลตัดสินใจว่ารหัสเดิมใช้เป็นข้อมูลกลางหรือเก็บประวัติแยกตามปี ก่อนเปลี่ยนคีย์ฐานข้อมูลและกติกาตรวจรหัสซ้ำ ตรวจว่าการปรับรองรับข้อมูลปี 2569
- ใช้ `--dry-run --verbose` บนฐานทดสอบเพื่อตรวจปีต้นทาง รายการที่จะเพิ่ม รหัสซ้ำ รหัสลูกที่หาแม่ไม่พบ และเหตุผลระดับแถว ใช้ Excel ปี 2569 เป็นชุดตรวจรับ โดยมีรหัสแม่ 15 รหัส รหัสลูก 75 รหัส และกิจกรรม 15 รหัส พิจารณาหน้าตรวจไฟล์เมื่อมีผู้ใช้งานประจำ [ตัวนำเข้า](../scripts/import_fiscal_codes.php) · [ชุดทดสอบ preflight](../tests/Unit/Scripts/FiscalImportPreflightTest.php)
- เก็บชื่อไฟล์ ปี ผู้ดำเนินการ เวลา และผลของแต่ละชุดนำเข้า การส่งไฟล์เดิมซ้ำต้องไม่เพิ่มรายการ และความล้มเหลวระหว่างบันทึกต้องไม่ทิ้งข้อมูลครึ่งชุด

### รายงานและการติดตาม

- หากเจ้าของรายงานต้องการยอดเงินตามกิจกรรม รหัสแม่ หรือหน่วยงาน ให้กำหนดคีย์เชื่อมกับรายการงบและวิธีจัดการรายการที่จับคู่ไม่ได้ ตรวจยอดรวมกับรายการต้นทางภายใต้ปีและขอบเขตเดียวกัน และตรวจว่าการเชื่อมข้อมูลไม่นับยอดซ้ำ
- ใช้แนวทาง NEXA ทำหน้าติดตามโครงการที่รวมสถานะคำขอ ยอดจัดสรร โอน ผูกพัน เบิกจ่าย คงเหลือ และเอกสารที่เชื่อมได้ ให้กดจากยอดไปดูรายการต้นทาง เพิ่มการบันทึกความคืบหน้าเมื่อกำหนดผู้รับผิดชอบแล้ว
- ต่อยอดรายงานรายไตรมาสและการเตือนจาก NEXA กับ `apps-script.txt` ให้เห็นรายการค้างอนุมัติ งานใกล้ครบกำหนด และผลต่างระหว่างแผนกับยอดจริง กำหนดเกณฑ์ ผู้รับ และความถี่ เพื่อให้ผู้รับรู้ว่าต้องเข้าไปทำรายการใด

### การควบคุมยอดและการอนุมัติ

- ใช้แนวคิดทะเบียนคุมจาก School Finance ให้ดูประวัติการเปลี่ยนยอดตามรายการจัดสรร โอน ผูกพัน และเบิกจ่าย พร้อมวันที่ ผู้ดำเนินการ และหลักฐาน ระบุช่วงที่ประวัติจากข้อมูลเดิมไม่ครบ
- ใช้ขั้นตอนจาก `apps-script.txt` เป็นแบบอ้างอิงหากฝ่ายงบประมาณต้องการอนุมัติการโอนในระบบ กำหนดผู้ขอ ผู้ตรวจ ผู้อนุมัติ และจังหวะเปลี่ยนยอด ตรวจยอดคงเหลือเมื่ออนุมัติ บันทึกการเปลี่ยนยอดต้นทางและปลายทางพร้อมกัน และเก็บประวัติการปฏิเสธ ยกเลิก หรือปรับปรุง
- ใช้แบบพิมพ์ของ Smart Budget เป็นตัวอย่างสำหรับเอกสาร A4 รวมคำขอ ปี แหล่งงบ รหัสงบ ยอดคงเหลือ ผู้อนุมัติ และหลักฐาน ระบุสถานะและวันที่ออกเอกสาร เพื่อให้แยกฉบับร่างจากฉบับอนุมัติได้
- ใช้แนวคิดรายงานเงินคงเหลือจาก School Finance เพื่อกระทบยอดกับเอกสารต้นทาง บันทึกผลต่างและผู้รับผิดชอบก่อนปิดงวด กำหนดสิทธิ์เปิดงวดใหม่หรือบันทึกรายการปรับปรุง พร้อมเหตุผลและผู้อนุมัติ

### สิทธิ์และความถูกต้อง

- ใช้ขอบเขตหน่วยงานเดียวกันสำหรับยอดรวม รายการที่เปิดจากรายงาน ไฟล์ส่งออก เอกสารแนบ และการแจ้งเตือน ตรวจทั้งหน้าเว็บและ API ด้วยผู้ใช้ต่างบทบาทและต่างหน่วยงาน
- ตรวจว่ายอดหน้าเว็บ รายการต้นทาง และไฟล์ส่งออกตรงกันเมื่อใช้ปี งวด และขอบเขตเดียวกัน ครอบคลุมรายการยกเลิก การทำรายการซ้ำ และการปรับปรุงหลังปิดงวด
- พิจารณาทะเบียนรับเงิน เงินนอกงบ รายงานเงินสด และ SAR เมื่อมีเจ้าของกระบวนงาน ผู้ใช้ และแหล่งข้อมูลชัดเจน

### ลำดับดำเนินงานและเกณฑ์ตรวจรับ

1. **ตรวจรับหน้ารายงานและผล preflight** ทำตามเกณฑ์ก่อนเผยแพร่ และตรวจผลระดับแถวก่อนเขียนข้อมูล
2. **ติดตามโครงการ ประวัติยอด และสรุปรายไตรมาส** เริ่มเมื่อระบุเจ้าของข้อมูล คีย์เชื่อม รอบส่ง และผู้รับได้ ผู้ใช้เปิดจากยอดสรุปถึงรายการต้นทางได้ และยอดในไฟล์ส่งออกตรงกับหน้ารายงาน
3. **แบบพิมพ์และการอนุมัติโอน** ให้เจ้าของงานยืนยันแบบพิมพ์ ผู้มีอำนาจอนุมัติ และจังหวะเปลี่ยนยอด ผู้ขอและผู้อนุมัติเห็นสถานะตรงกัน การอนุมัติซ้ำไม่เปลี่ยนยอดซ้ำ และตรวจหลักฐานย้อนหลังได้
4. **กระทบยอดและปิดงวด** ติดตามผลต่างกับเอกสารต้นทางได้ และรายการปรับปรุงหลังปิดงวดมีเหตุผลกับผู้อนุมัติ
