## 2. โครงสร้างรหัส (ถอดรหัสแล้ว)

### 2.1 รูปแบบ 20 หลัก (รหัสลูก / ระดับรายการ)

```
ตำแหน่ง  1        6       7-8      9-10     11-12    13-15     16-20
         [AGC]  [ปี/แหล่ง] [กิจกรรม] [ย่อย]  [หมวด]   [หมวดจ่าย] [ลำดับ]
ตัวอย่าง  16002    6         10       00       30        031        20001
```

| ช่วง | ความยาว | ความหมาย | ค่าที่พบในข้อมูล |
| --- | --- | --- | --- |
| `AGC` | 5 | รหัสหน่วยงานต้นสังกัด | `16002` (เสมอ) |
| ปีงบ/แหล่ง | 1 | กลุ่มแหล่งงบ | `0`, `1`, `5`, `6` |
| กิจกรรม | 2 | รหัสกิจกรรมหลัก/ย่อย | `00 10 11 12 30 31 32 40 42 70 80 90 91` |
| ย่อย | 2 | รหัสย่อยของกิจกรรม | `00`, `01` |
| หมวด | 2 | กลุ่มหมวดรายจ่าย | `00 01 10 20 30 40 50 70 80 90` |
| **หมวดจ่าย** | 3 | **ประเภทรายจ่าย (สำคัญที่สุด)** | `010 020 031 032 041 050` |
| ลำดับ | 5 | เลขลำดับรายการ | `00000` (รหัสแม่), `00001`–`20010` |

### 2.2 รูปแบบ 13 หลัก (รหัสแม่ / ระดับโครงการ)

```
ตำแหน่ง  1        6       7-8      9-10     11-13
         [AGC]  [ปี/แหล่ง] [กิจกรรม] [ย่อย]  [รหัสรวม]
ตัวอย่าง  16002    6         10       00       300
```

รหัสแม่ 13 หลัก = รหัสลูก 20 หลักตัด 7 หลักท้ายออก → ใช้เป็นตัวรวมยอด (parent rollup) ใน UI ได้โดยตรง

### 2.3 รูปแบบ 17 หลัก (รหัสกิจกรรมหลัก — จากไฟล์ `.xls`)

```
ตำแหน่ง  1        6       7-8      9-10     11-12    13-17
         [AGC]  [ปี/แหล่ง] [กิจกรรม] [ย่อย]  [หมวด]   [ลำดับ 5 หลัก = 00000]
ตัวอย่าง  16002    6         90       00       38       00000
```

สังเกต: รหัสกิจกรรมหลักใน `.xls` มี `38` วางที่ตำแหน่ง 11-12 ซึ่งเป็นตำแหน่ง "หมวด" ของรหัส 20 หลัก → โครงสร้างส่วนต้น (AGC+ปี+กิจกรรม+ย่อย+หมวด) ตรงกัน แต่ **รหัสกิจกรรมหลักเป็นระบบคำอธิบายแยกต่างหาก** ไม่ใช่แค่ตัดท้ายรหัส 20 หลัก — ต้องเก็บทั้งสองระบบแยกกัน (activity_code 17 หลัก สำหรับ join กับตาราง `plans`)

## 4. การนำไปใช้จริง

### 4.1 Taxonomy: ขยาย `expense_types` ไม่สร้างตารางใหม่

`budget_types` (`BUK`/`UNIT`/`INTEG`) เป็นการจัดประเภทแบบ **แหล่งงบ** ส่วน fiscal code 6 หมวดเป็น **ประเภทรายจ่าย** คนละมิติกัน

ข้อเสนอเดิมในเอกสารนี้คือสร้างตาราง `expense_categories` ใหม่ แต่ข้อเสนอนั้นถูกยกเลิกเพราะ `expense_types` มีอยู่แล้วตั้งแต่ migration `022_create_expense_types.sql` และมีตารางอื่นถือ `expense_type_id` อยู่หลายตาราง การสร้างตารางใหม่จะทำให้เกิด taxonomy สองชุดที่ไม่ตรงกัน

สิ่งที่ทำจริงใน migration `094_add_fiscal_code_to_expense_types.sql` คือเพิ่ม `fiscal_code CHAR(3)` ให้ `expense_types`, ใส่รหัส `010/020/041` บนแถวเดิมที่ตรงกัน และเพิ่มแถวใหม่สำหรับ `031/032/050`. ส่วน `งบลงทุน` และ `งบรายจ่ายอื่น` ไม่มีในข้อมูลต้นทางจึงปล่อย `fiscal_code` เป็น NULL. ชื่อไทยของแถวเดิมที่เคยเสียเป็น `?` ถูกซ่อมด้วย `scripts/seed_expense_type_fiscal_codes.php` ตามโค้ดจริงใน PR #89

รหัสของแต่ละแถวใช้รูปแบบ `ET-` ตามด้วย `substr(md5(name_th), 0, 4)` ตามที่ importer เดิมใช้ ตัวอย่าง `ET-dda6` คือ `งบบุคลากร` และได้ `fiscal_code = '010'`.

### 4.2 คอลัมน์และดัชนีที่เพิ่มจริง

migration `095_add_fiscal_code_columns.sql` เพิ่มคอลัมน์แบบ NULL ได้ทั้งหมดเพื่อไม่บล็อกข้อมูลเดิม ดังนี้

| ตาราง | คอลัมน์ที่เพิ่ม |
| --- | --- |
| `budget_categories` | `fiscal_code CHAR(20)`, `fiscal_code_parent CHAR(13)`, `activity_code CHAR(17)`, `expense_cat_code CHAR(3)` |
| `plans` | `activity_code CHAR(17)` |
| `projects` | `fiscal_code CHAR(20)` |

ดัชนีที่สร้างคือ `uk_fiscal_code` บน `budget_categories` และ `projects`, `idx_fiscal_parent`, `idx_activity_code` บน `budget_categories` และ `plans`, และ `idx_expense_cat` บน `budget_categories`. migration และ rollback เขียนแบบมี `information_schema` guard จึงรันซ้ำได้.

migration `096_seed_fiscal_agency_division.sql` เพิ่ม `divisions` แถว `16002 → สำนักงานปลัดกระทรวงยุติธรรม` จากบรรทัดที่ 2 ของ `16002_กิจกรรมหลัก.xls` เพื่อให้ report แสดงชื่อหน่วยงานแทน `null`. rollback ของ 096 ลบเฉพาะแถวที่ชื่อตรงกับต้นทาง

### 4.3 Validation รูปรหัส

`src/Helpers/FiscalCode.php` เป็น pure helper ที่มี `EXPENSE_CATEGORIES` เป็น constant map ของ 6 หมวด และเมธอด `isValid20`, `parent13`, `expenseCategory`, `isValidExpenseCategory`, `isValidActivityCode`, `activityGroup`. regex ใช้ `\z` ไม่ใช้ `$` เพื่อปฏิเสธข้อความที่มี LF ท้าย. `isValidExpenseCategory` เรียก `isValid20` ก่อน จึงไม่ยอมรับสตริงสั้นที่ลงท้ายด้วยรหัสหมวดที่ถูกต้อง.

helper นี้ถูกเรียกที่ boundary ใน DTO ของ category/plan และตอน import. Controller ไม่ต้องเปลี่ยนเพราะ `validate()` เดิมแปลง error เป็น 422 อยู่แล้ว. ข้อความ error เป็นภาษาไทย เช่น `รหัสงบประมาณต้องมี 20 หลัก` และ `รหัสกิจกรรมหลักต้องมี 17 หลัก`.

### 4.4 ขั้นที่ 3 — Import script

```php
// scripts/import_fiscal_codes.php
// อ่าน 16002_รหัสงบประมาณ.xlsx แล้ว seed เข้า budget_categories / plans
// - แถว 13 หลัก → budget_categories (parent)
// - แถว 20 หลัก → budget_categories (child, parent_id = แถวแม่)
// - 15 activity rows จาก .xls → plans.activity_code
// - idempotent: ข้ามแถวที่ fiscal_code/activity_code มีอยู่แล้ว
```

script จริงคือ `scripts/import_fiscal_codes.php` และ config คือ `config/import_fiscal_codes.php`. มันอ่าน spreadsheets ด้วย PhpSpreadsheet, ใช้ transaction, และบังคับ `--database=NAME` ที่ลงท้าย `_test` ก่อนเขียนใด ๆ. ไม่ได้ parse ชื่อจังหวัด. จากข้อมูลจริง 45/90 แถวมีชื่อจังหวัดฝังอยู่ แต่การจับคู่กับ `provinces` ยังไม่ได้ทำ. ถ้าจะเพิ่ม ต้องใช้รายชื่อจังหวัดทั้ง 77 แบบ canonical และเก็บเป็นงานแยก.

## 6. ข้อควรระวัง

**เรื่องข้อมูล**
- `AGC` ทั้งไฟล์เป็น `16002` เดียว → ยังไม่ยืนยันว่าโครงสร้างเดียวกันใช้ได้กับทุกหน่วยงาน
- PDF มี text layer แต่ข้อความไทยเสียและเป็นปี 2570 ไม่ใช่ 2569 จึงไม่ใช้เป็นแหล่ง import และไม่ต้อง OCR
- ชื่อจังหวัดฝังในข้อความอิสระ 45/90 แถว ถ้าจะเชื่อมกับ `provinces` ต้องใช้รายชื่อจังหวัดทั้ง 77 แบบ canonical และแยกเป็นงานใหม่

**เรื่องสถาปัตยกรรม**
- `expense_types` เป็นที่เก็บหมวดรายจ่ายตัวเดียว `budget_types` (BUK/UNIT/INTEG) เป็นคนละมิติ ห้ามสร้าง `expense_categories` ซ้ำ
- รหัส 20 หลักใช้ `CHAR(20)` และมี `uk_fiscal_code` เพื่อให้ import idempotent
- import script ปฏิเสธชื่อ database ที่ไม่ลงท้าย `_test` ถ้าจะรัน production ต้องใช้ one-off runner และ backup ก่อนเท่านั้น
- อย่าใช้ `fix_encoding`/`fixEncoding` จาก importer เก่ากับ UTF-8 ที่สะอาด เพราะมันแปลงไทยเป็น `?`

**เรื่องความสอดคล้องกับระบบเดิม**
- migration มี collisions เดิมที่ `022`/`023`/`024` → ต้องเช็ค `database/migrations/` ก่อนตั้งหมายเลขใหม่
