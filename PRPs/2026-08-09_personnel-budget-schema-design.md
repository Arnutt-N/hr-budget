## สิ่งที่ฐานข้อมูลจริงมีอยู่แล้ว — อย่าสร้างซ้ำ

ฉบับแรกออกแบบโดยไม่รู้ว่า hr_budget **มีโครงรายการงบบุคลากรครบแล้ว**

```
expense_types (5 แถว)
  1 งบบุคลากร ─┬─ expense_groups 1 เงินเดือนและค่าจ้างประจำ
               │     ├─ ei 1  เงินเดือน ─┬─ ei 2 อัตราเดิม   ⭐ prorate ที่ปลอมตัวมา
               │     │                    ├─ ei 3 อัตราใหม่
               │     │                    └─ ei 4 เงินอื่นที่จ่ายควบกับเงินเดือน
               │     │                          ├─ ei 5  เงินประจำตำแหน่ง (+3 ประเภทย่อย)
               │     │                          ├─ ei 12 ค่าตอบแทนรายเดือน**เท่ากับ**เงินประจำตำแหน่ง ⭐
               │     │                          ├─ ei 17 เงินช่วยเหลือการครองชีพข้าราชการระดับต้น
               │     │                          ├─ ei 18 พ.ต.ก. · ei 19 พ.พ.ด.
               │     │                          └─ ei 20 พ.ส.ร. · ei 21 สปพ.
               │     └─ ei 22 ค่าจ้างประจำ  (อัตราเดิม/ใหม่ + เงินอื่นที่จ่ายควบ — โครงเดียวกัน)
               └─ expense_groups 2 ค่าตอบแทนพนักงานราชการ
                     └─ ei 29 (อัตราเดิม/ใหม่ + เงินอื่นที่จ่ายควบ — โครงเดียวกัน)

  2 งบดำเนินงาน ── expense_groups 3 ค่าตอบแทนใช้สอยและวัสดุ
                     └─ ei 35 **ค่าเช่าบ้าน**   ← ไม่ได้อยู่ในงบบุคลากร
```

⭐ **`ei 12` คือ "ค่าตอบแทนนอกเหนือจากเงินเดือน" ที่หัวข้อ ④ วิเคราะห์ไว้ยาว** — ชื่อทางการมีคำว่า
**"เท่ากับ"** อยู่ในตัว = derivation rule ที่ถูกประกาศเป็นทางการอยู่แล้ว ⇒ `derives_from_type_id`
ไม่ใช่การประดิษฐ์เอง แต่เป็นการทำให้กฎที่ซ่อนในชื่อกลายเป็นข้อมูลที่ query ได้

⭐ **`อัตราเดิม / อัตราใหม่`** โผล่ครบทั้ง 3 ประเภท = เจ้าหน้าที่ทำ prorate ด้วยมือผ่านโครงสร้าง
รายการอยู่ทุกปี (อัตราใหม่บรรจุกลางปี ไม่กินงบเต็ม 12 เดือน) ⇒ ตอบคำถามข้อ 1 ไปครึ่งหนึ่ง

### แกนบัญชี ≠ แกนบริหาร (ค้นพบ 2026-08-10)

ผู้ใช้ยืนยันว่าค่าเช่าบ้านอยู่งบดำเนินงาน **"ถูก แต่ต้องรายงานรวมกัน"** ⇒ มีสองแกนที่ไม่ตรงกัน

| | แกนบัญชี | แกนบริหาร |
|---|---|---|
| คุมโดย | `expense_items.expense_type_id` (กฎหมายงบประมาณ) | `allowance_types.report_scope` ⭐ ของใหม่ |
| ค่าเช่าบ้าน | งบดำเนินงาน | นับรวมใน "ภาพรวมค่าใช้จ่ายบุคลากร" |
| ห้าม | แก้ `expense_type_id` ให้ตรงใจผู้บริหาร | เอา `report_scope` ไปลงเอกสารราชการ |

**ยัดสองแกนนี้เป็นแกนเดียวเมื่อไหร่ = report ตัวเลขไม่ตรงกับเอกสารงบประมาณทันที**

## ทำไมต้องมีเอกสารนี้

hr_budget วันนี้รับ **งบบุคลากร** เป็นตัวเลขที่พิมพ์เข้าไปใน `budget_line_items` เหมือนรายการอื่น
แต่ความจริงมันเป็นตัวเลขที่ **คำนวณได้** จากอัตรากำลัง และตรวจย้อนได้ถึงรายตำแหน่ง

สกีมาระบบเดิมมีตัวตั้งครบ (`per_position.pos_salary`, `pos_mgtsalary`, `pay_no` เลขถือจ่าย)
สิ่งที่ hr_budget ขาดคือ **แนวคิด "ตำแหน่ง"** ทั้งแนวคิด

```
hr_budget วันนี้:   organizations ────────?──────── users   (users.department = VARCHAR อิสระ)
ระบบเดิม:          per_org ──< per_position >── per_personal
                              (อัตรากำลัง)      (ตัวคน)
```

**ตำแหน่ง ≠ ผู้ใช้** อัตราว่างที่ยังไม่มีคนครองก็มีตัวตนและอาจกินงบ ถ้าเอา "ตำแหน่ง" ไปผูกกับ
ตาราง `users` จะคำนวณงบผิดทันที

## บริบทโดเมนจากผู้ใช้ (อ่านจากโค้ดหรือสกีมาเองไม่ได้)

1. **ตำแหน่งเปลี่ยนได้ทุกปี หรือไม่เปลี่ยนเลย** — ยุบตำแหน่ง เปลี่ยนชื่อ เปลี่ยนระดับ
   เลขที่ตำแหน่งก็เปลี่ยนได้ · การเปลี่ยนระดับอาจทำให้**เกิดสิทธิ์เงินประจำตำแหน่งเพิ่ม**
2. **อัตราว่างไม่ได้นับทุกอัตรา** — นับเฉพาะอัตราพร้อมบรรจุ หรือที่มีประกาศสรรหาแล้ว
   (หนังสือขอรับโอน · ประกาศขึ้นบัญชี)
3. **มีเงินเพิ่มอื่นๆ อีกหลายประเภท** — พ.ต.ก. · พ.ส.ร. · ส.ป.พ. ฯลฯ (รายการยังไม่ครบ)
4. ~~บุคลากรมี 4 ประเภท~~ → **3 ประเภท**: ข้าราชการ · พนักงานราชการ · ลูกจ้างประจำ
   — แต่ละประเภทเป็นรายการแยกกันในงบบุคลากร
   **แก้ 2026-08-10:** ผู้ใช้ยืนยัน *"ลูกจ้างชั่วคราวไม่มีจริง ไม่ต้องรองรับ"* และ DB จริงก็ไม่มี
   `expense_item` ของค่าจ้างชั่วคราวเลย ⇒ `employee_category` มี **3 ค่า** ห้ามใส่ค่าที่ 4 เผื่อไว้
   (จะกลายเป็น branch ที่ไม่มีวันทำงาน แล้วไม่มีใครกล้าลบ)
5. **ตั้งงบทำช่วง พ.ย.–ธ.ค.** คือ *หลัง* ต้นปีงบ (1 ต.ค.) ไปแล้ว 1–2 เดือน ⇒ ณ วันตั้งงบ
   การเลื่อนเงินเดือนรอบ 1 ต.ค. **เสร็จบางหน่วย ยังไม่เสร็จบางหน่วย** พร้อมกัน
   ⇒ `base_salary` ของคนละหน่วยงานมีความน่าเชื่อถือไม่เท่ากัน — ดูหัวข้อ [การเลื่อนเงินเดือน](#การเลื่อนเงินเดือน--ตัวแปรที่ทำให้-base_salary-ไม่นิ่ง)

## สิ่งที่สกีมาเดิมสอน

### ① ตำแหน่งเป็นสิ่งที่มีอายุ (temporal) — แหล่งความจริงคือตารางประวัติ

`per_pos_move` **PK = (pos_id, pos_date)** เก็บคอลัมน์เงินซ้ำทั้งชุด: `pos_salary`,
`pos_mgtsalary`, `level_no`, `pl_code`, `org_id`, `pay_no`, `pos_doc_no`

คำถาม "ตำแหน่งนี้เงินเดือนเท่าไหร่" ตอบไม่ได้ ต้องถามว่า **"ณ วันไหน"**

`per_position` เป็นเพียง **cache ของสภาพล่าสุด** ไม่ใช่แหล่งความจริง

### ② ทุกเวอร์ชันอ้างคำสั่งที่ทำให้เปลี่ยน

`pos_doc_no` (เลขที่คำสั่ง) อยู่ในทุกแถวประวัติ — เงินไม่เปลี่ยนเอง มันเปลี่ยนเพราะมีคำสั่ง
ระบบงบประมาณราชการต้องตอบผู้ตรวจได้ว่า "ตัวเลขนี้มาจากคำสั่งฉบับไหน" → **ลอกแนวคิดนี้มาทั้งดุ้น**

### ③ แยก "สิทธิ์" ออกจาก "การรับจริง" ← สำคัญที่สุดสำหรับงบ

```
per_extratype.mgt_flag   0 = เงินเพิ่มพิเศษ (พ.ต.ก. / พ.ส.ร. / ส.ป.พ. ...)
                         1 = เงินประจำตำแหน่ง

สิทธิ์   per_pos_mgtsalary     PK (pos_id, ex_code)  → ผูกกับ*ตำแหน่ง*
                                ไม่มีคอลัมน์จำนวนเงิน — บอกแค่ "ตำแหน่งนี้มีสิทธิ์รับประเภทนี้"

รับจริง  per_pos_mgtsalaryhis  per_id + pmh_amt + ช่วงวันที่   → ผูกกับ*คน*
         per_extrahis          per_id + exh_amt + exh_docno   → ผูกกับ*คน*
```

**อัตราว่างมีสิทธิ์ แต่ไม่มีการรับจริง** ⇒

| | ใช้อะไร |
|---|---|
| ตอน**ตั้งงบ** (ยังไม่รู้ว่าใครจะครอง) | **สิทธิ์** ระดับตำแหน่ง |
| ตอน**เบิกจ่ายจริง** | **การรับจริง** ระดับคน |
| **ผลต่าง** | งบที่ตั้งไว้แต่ไม่ได้ใช้ ← ตัวเลขที่ผู้บริหารอยากรู้ที่สุด |

ผลต่างนี้เกิดจริง เช่น ตำแหน่งมีสิทธิ์ พ.ต.ก. แต่คนที่ครองยังไม่ผ่านการประเมิน

### ④ เงินเพิ่มบางตัว "อ้างอิงเงินเพิ่มตัวอื่น" — สกีมาเดิมแสดงไม่ได้

**ค่าตอบแทนนอกเหนือจากเงินเดือน** (ยืนยันโดยผู้ใช้ 2026-08-09):

```
ถ้า ระดับ ∈ { ชำนาญการพิเศษ, เชี่ยวชาญ, ทรงคุณวุฒิ, อำนวยการ*, บริหาร* }:
      มีเงินประจำตำแหน่ง = X  →  ค่าตอบแทนนอกเหนือฯ = X       (เท่ากันเป๊ะ)
      ไม่มีเงินประจำตำแหน่ง   →  3,500 เฉพาะ "ชำนาญการพิเศษ" เท่านั้น
                                 ระดับอื่นได้ 0
มิฉะนั้น (ชำนาญการ ลงมา, ประเภททั่วไป):  →  0
```

**ยืนยันโดยผู้ใช้ (2026-08-09):**
- `3,500` เป็น fallback ของ **ชำนาญการพิเศษ เท่านั้น** ไม่ใช่พื้นของทุกระดับที่มีสิทธิ์
- **เชี่ยวชาญ / ทรงคุณวุฒิ** นับอยู่ในกลุ่ม "ชำนาญการพิเศษขึ้นไป" → มีสิทธิ์
- **`scope = 'position'`** — ผูกกับตำแหน่ง ⇒ **อัตราว่างที่มีเงิน (และผ่านเกณฑ์สรรหา)
  ต้องรวม ค.ต.น. เข้างบด้วย**
- ประเภททั่วไป (ปฏิบัติงาน/ชำนาญงาน/อาวุโส/ทักษะพิเศษ) ไม่ถูกระบุ ⇒ ไม่มีแถว ⇒ ได้ 0
  แม้บางระดับจะมีเงินประจำตำแหน่งก็ตาม

| ตำแหน่ง | เงินประจำตำแหน่ง | ค่าตอบแทนนอกเหนือฯ | รวม/เดือน |
|---|---:|---:|---:|
| นักวิชาการคอมพิวเตอร์ ชำนาญการ | 3,500 | 0 | 3,500 |
| นักวิชาการคอมพิวเตอร์ ชำนาญการพิเศษ | 5,600 | 5,600 | 11,200 |
| ชำนาญการพิเศษ (ไม่มีเงินประจำตำแหน่ง) | 0 | 3,500 | 3,500 |

**ผลต่อการเลื่อนระดับ** ชำนาญการ → ชำนาญการพิเศษ 1 ตำแหน่ง:

| วิธีคิด | ต่อเดือน | ต่อปี |
|---|---:|---:|
| ผิด — ดูแค่เงินประจำตำแหน่ง (5,600 − 3,500) | 2,100 | 25,200 |
| **ถูก** — (11,200 − 3,500) | **7,700** | **92,400** |

คิดผิดไป **67,200 บาท/ปี/ตำแหน่ง** (ต่ำกว่าจริง 3.7 เท่า) ยังไม่รวมเงินเดือนที่ขึ้น

**ทำไมสกีมาเดิมแสดงไม่ได้:** `per_extratype` มีแค่ `ex_amt` (จำนวนเงินก้อนเดียว) ไม่มีช่อง
อ้างอิงเงินเพิ่มตัวอื่น และไม่มีช่องระดับตำแหน่ง ⇒ ระบบเดิมทำได้ทางเดียวคือคำนวณข้างนอก
แล้วเก็บตัวเลขสำเร็จลง `per_extrahis.exh_amt` (รายคน) ⇒ **ตั้งงบสำหรับอัตราว่างไม่ได้**
เพราะอัตราว่างไม่มีคน จึงไม่มีแถวประวัติ

นี่คือเหตุผลที่ `allowance_rates` ต้องแยกออกมาและต้องรองรับ derivation

### ⑤ เงินเพิ่มที่ผูกกับ "คน" — งบบุคลากรจึงคำนวณได้ไม่หมด

**เงินค่าเช่าบ้าน** (ยืนยันโดยผู้ใช้ 2026-08-09): `scope = 'personal'` · **ได้แค่บางคน**

สิทธิ์ไม่ได้ตัดสินจากระดับ/สายงานของตำแหน่ง แต่จากสถานการณ์ส่วนตัว — ตำแหน่งเดียวกัน
ระดับเดียวกัน สองคน คนหนึ่งได้ อีกคนไม่ได้ ⇒ **อนุมานจากข้อมูลอัตรากำลังไม่ได้เลย**

| | scope='position' (ค.ต.น., เงินประจำตำแหน่ง) | scope='personal' (ค่าเช่าบ้าน) |
|---|---|---|
| สิทธิ์ตัดสินจาก | ระดับ + สายงานของตำแหน่ง | สถานการณ์ส่วนตัว |
| อัตราว่างได้ไหม | ได้ | **ไม่ได้เลย** |
| ตั้งงบจากอัตรากำลัง | ได้ | **ไม่ได้** |

**⇒ แก้ข้อสรุปเดิมของเอกสารนี้:** งบบุคลากรไม่ได้คำนวณจากอัตรากำลังได้ทั้งก้อน ต้องแยก 2 ส่วน

```
❌ ผิด (ฉบับ 2026-08-09):
งบบุคลากร =  ส่วนที่คำนวณได้     (scope='position')
           +  ส่วนที่ต้องประมาณ  (scope='personal')   ← ค่าเช่าบ้านไม่ได้อยู่หมวดนี้

✅ ถูก (แก้ 2026-08-10 หลังตรวจ DB จริง):
งบบุคลากร (expense_type=1)         = scope='position' ล้วน  ← คำนวณจากอัตรากำลัง 100%
งบดำเนินงาน/ค่าตอบแทน (=2) ⊃ ค่าเช่าบ้าน scope='personal'   ← คนละหมวด คนละวิธีคำนวณ

รายงาน "ภาพรวมค่าใช้จ่ายบุคลากร" (แกนบริหาร) = ทั้งสองก้อนรวมกัน
   ← ผู้ใช้ยืนยัน 2026-08-10: "ถูก แต่ต้องรายงานรวมกัน"
   ← คุมด้วย allowance_types.report_scope ห้ามคุมด้วย expense_type_id
```

**ข่าวดี:** งบบุคลากรสะอาดกว่าที่ฉบับแรกคิด — ตรวจย้อนถึงรายตำแหน่งได้ทั้งก้อน
ส่วนที่ประมาณไม่ได้ถูกดันออกไปนอกหมวดตั้งแต่ต้นทางแล้ว

**อีกจุดที่ต่าง: อัตราเป็น "เพดาน" ไม่ใช่ "จำนวนที่จ่าย"** — ค่าเช่าบ้านจ่ายตามจริงโดยมีเพดาน
ตามระดับ ถ้าเอาเพดานมาบวกกันจะได้งบที่สูงเกินจริง จึงต้องมี `rate_kind` แยกความหมายของ
`allowance_rates.amount` ระหว่าง "จำนวนที่จ่ายแน่นอน" กับ "เพดาน"

**ผลต่อ insight เรื่องสิทธิ์ vs รับจริง:** ใช้ได้เฉพาะ `scope='position'` เพราะฝั่ง personal
ไม่มีเส้นฐาน "สิทธิ์" ให้เทียบตั้งแต่ต้น

#### วิธีตั้งงบค่าเช่าบ้าน (ยืนยันโดยผู้ใช้ 2026-08-09)

> **"ยอดปัจจุบัน คำนวณตั้งเบิก"**

```
งบค่าเช่าบ้าน(ปีงบ Y)
  = Σ คนที่ *กำลังรับอยู่* ณ วันอ้างอิง × จำนวนที่รับปัจจุบัน × เดือนที่นับ
```

`budget_basis = 'actuals'` — แต่เจาะจงกว่านั้น: เป็น **snapshot ของผู้รับ ณ ปัจจุบัน**
ไม่ใช่ยอดรวมของปีก่อน ⇒ รูปแบบการคำนวณ**เหมือนฝั่งตำแหน่งทุกประการ** ต่างแค่ว่า
วนรอบ *คน* แทน *ตำแหน่ง*:

```
ฝั่งตำแหน่ง : Σ ตำแหน่งที่มีผล ณ วันอ้างอิง  × อัตรา × เดือน
ฝั่งคน      : Σ คนที่รับอยู่ ณ วันอ้างอิง    × ยอดจริง × เดือน
```

**ความคลาดเคลื่อนที่ต้องยอมรับ** — snapshot มองไม่เห็นการเปลี่ยนแปลงระหว่างปี:

| กรณี | ผลต่องบ |
|---|---|
| คนใหม่ย้ายมาระหว่างปีแล้วขอค่าเช่าบ้าน | งบ**ต่ำกว่า**จริง |
| คนที่ยังไม่ได้ยื่นขอ (มีสิทธิ์แต่ยังไม่ใช้) | งบ**ต่ำกว่า**จริง |
| คนที่หมดสิทธิ์ระหว่างปี (ซื้อบ้าน/ย้ายกลับ) | งบ**สูงกว่า**จริง |

⇒ ควรมีช่องปรับ (buffer/adjustment %) ที่ระดับ `personnel_budget_policy` ไม่ใช่ไปแก้ยอดรายคน

#### เพดานตามระดับ — ยังไม่ทราบ แต่ **ไม่บล็อกงาน**

ผู้ใช้ตอบว่าไม่แน่ใจว่าเพดานค่าเช่าบ้านแบ่งตามระดับหรือไม่

**ไม่ต้องรู้ก็เริ่มได้** เพราะการตั้งงบใช้ *ยอดจริงที่รับอยู่* ไม่ได้ใช้เพดาน
`allowance_rates` สำหรับ type นี้จึง **เว้นว่างไว้ได้** — เพดานมีประโยชน์เฉพาะตอน
*ตรวจสอบคำขอเบิก* ว่าไม่เกินสิทธิ์ ซึ่งเป็นฟีเจอร์คนละตัวและทำทีหลังได้

นี่คือเหตุผลที่ `rate_kind` ต้องมี: บอกว่าตัวเลขใน `allowance_rates` ของ type นี้ (ถ้าวันหนึ่ง
เติมเข้าไป) เป็น**เพดานสำหรับตรวจสอบ** ไม่ใช่**ยอดสำหรับตั้งงบ**

## การเลื่อนเงินเดือน — ตัวแปรที่ทำให้ `base_salary` ไม่นิ่ง

> บริบทจากผู้ใช้ 2026-08-10 · เรื่องนี้ไม่มีในสกีมาระบบเดิม และฉบับแรกไม่ได้คิดถึงเลย

### ปัญหา: ตั้งงบตอนที่ข้อมูลยังมาไม่ครบ

```
1 ต.ค. ─────────────── พ.ย.–ธ.ค. ────────────────▶ ปีงบ Y
   │                        │
   │ รอบเลื่อนเงินเดือน      │ ตั้งงบตอนนี้ ← ข้อมูลยังมาไม่ครบ
   │
   ├─ บางหน่วย: เลื่อนเสร็จ  → ใช้ตัวเลขจริง       ✅ actual
   └─ บางหน่วย: ยังไม่เสร็จ  → ต้องประมาณการ      ⚠️ estimated
```

**ห้ามใช้ `organizations.region` เป็นตัวตัดสิน** — ผู้ใช้ยืนยัน *"แล้วแต่หน่วย ไม่ตายตัว"*
(`region` มี 4 ค่าใน DB จริง: `central` / `regional` / `provincial` / `central_in_region`
กลุ่มสุดท้ายคือส่วนกลางที่ตั้งอยู่ในภูมิภาค ซึ่งคาบเกี่ยวทั้งสองฝั่ง)
⇒ ต้องเก็บสถานะ**รายหน่วยงาน**เป็นข้อมูล `region` เป็นได้แค่ตัวช่วยกรองตอนกรอก

### กติกาการประมาณ (ยืนยัน 2026-08-10)

### ไปช่วยราชการ — งบอยู่ต้นสังกัด แต่ต้องเห็นว่าใครไปไหน

ผู้ใช้ยืนยัน: **"หน่วยต้นสังกัด แต่ต้องดูแยกได้"**

```
ตำแหน่ง (เจ้าของงบ)          คน (ที่ไปทำงานจริง)

        ▲                                    ▲
   GROUP BY ตัวนี้เสมอ                รายงานอย่างเดียว
   ตอนคิดยอดงบ                        ห้ามใช้ GROUP BY ยอดงบ
```

**ทำไมห้ามย้ายงบตามตัวคน:** ตำแหน่งคือหน่วยที่ผูกกับอัตรากำลังและคำสั่ง ถ้ายอดงบเลื่อนไหลตาม

### รอบเลื่อน — รองรับหลายรอบ เปิดใช้รอบเดียว

ผู้ใช้: *"ออกแบบให้รองรับไว้ … แต่ตอนเริ่มคิดรอบ ต.ค. ปีปัจจุบันอย่างเดียว"*

```
salary_raise_rounds
  (เม.ย. 2568) include_in_budget = 0
  (ต.ค.  2568) include_in_budget = 1   ← เปิดใช้ตอนนี้  (ต้นปีงบ 2569)
  (เม.ย. 2569) include_in_budget = 0   ← กลางปีงบ 2569 · แถวมีอยู่ สวิตช์ปิด
  (ต.ค.  2569) include_in_budget = 0
```

**ทำไมสร้างแถวไว้ทั้งที่ยังไม่ใช้:** เปิดใช้วันหน้าคือ `UPDATE ... SET include_in_budget=1`
ไม่ใช่ migration ใหม่ + แก้สูตร · และแถวที่ปิดอยู่ก็ยังเก็บสถานะการเลื่อนจริงได้
(มีประโยชน์ตอนย้อนดูว่าเงินเดือนขึ้นเมื่อไหร่) โดยไม่กระทบยอดงบ

### รายงานที่ได้ฟรีจากโครงนี้

การเก็บ *"ตัวเลขนี้เชื่อได้แค่ไหน"* ไม่ได้แค่ทำให้คำนวณถูก — มันเปิดรายงานที่วันนี้ทำไม่ได้เลย

| รายงาน | ที่มา |
|---|---|
| งบส่วนที่ยังเป็นการประมาณ คิดเป็น % | `SUM(...) WHERE salary_basis='estimated'` |
| จังหวัดที่ยังไม่เลื่อนเงินเดือน (ตามทวง) | `salary_raise_progress WHERE status='pending'` |
| ผลต่าง ประมาณ vs จริง หลังเลื่อนครบ | `salary_pre_raise` เทียบยอดใหม่ ⇒ ประมาณสูง/ต่ำไปเท่าไหร่ |
| คนไปช่วยราชการ อยู่หน่วยไหนบ้าง | `personnel_assignments.serving_organization_id` |
| ตำแหน่งที่ชนเพดานขั้นสูงแล้ว | `base_salary ≥ salary_scales.max_amount` ⇒ เลื่อนได้น้อยกว่า 3% |

**จุดที่ต้องระวังในการแสดงผล:** ยอดที่มี `estimated` ปนอยู่ **ต้องติดป้ายเสมอ** อย่าโชว์เป็น
ตัวเลขเดียวกับยอดที่ยืนยันแล้ว — ไม่งั้นจะมีคนเอาไปอ้างในที่ประชุมโดยไม่รู้ว่ามันคือการเดา

**หมายเหตุลูกโซ่:** เงินเพิ่มที่คิดเป็น `percent_of_salary` จะ**สืบทอดความไม่แน่นอน**มาด้วย
ถ้า `salary_basis='estimated'` ยอดเงินเพิ่มตัวนั้นก็ประมาณตามไปโดยอัตโนมัติ — ไม่ต้องทำอะไรเพิ่ม
แต่ตอนรายงานต้องนับรวมอยู่ในก้อน "ประมาณ" ด้วย

### สูตร

```
งบบุคลากร(ปีงบ Y, หน่วยงาน O)          -- expense_type=1 · แกนบัญชี · ลงเอกสารราชการได้
= Σ  ตำแหน่ง p ที่ version มีผล ณ reference_date(Y)
       AND version.organization_id  = O
       AND version.lifecycle        = 'active'
       AND version.approval_status  = 'approved'          ⭐ ไม่รวมคำขอที่ยังไม่อนุมัติ
       AND ( occupancy = 'occupied'
             OR ( occupancy = 'vacant_funded' AND ผ่าน vacancy_rule(p, Y) ) )

     m(p) = ( calc_mode='snapshot' ) ? 12 : version.months_counted   ⭐ prorate รายตำแหน่ง

     [  projected_salary(p, Y) × m(p)                    ⭐ ไม่ใช่ base_salary ดิบ
      + Σ สิทธิ์ a ใน position_allowances(p) ที่มีผล
          AND a.expense_item อยู่ใต้ expense_type=1        ⭐ กรองด้วยแกนบัญชี
          AND ( occupancy='occupied' OR a.vacant_eligible ) ⭐ นโยบาย ไม่ใช่ scope
          → rate(a, p) × m(p)  ]

ค่าใช้จ่ายบุคลากรที่อยู่นอกงบบุคลากร(Y, O)   -- แกนบริหาร · ห้ามลงเอกสารราชการ
= Σ  a ที่ a.report_scope ⊃ 'personnel'  AND  a.expense_item ไม่ได้อยู่ใต้ expense_type=1
     budget_basis='actuals' → snapshot ของผู้รับ ณ วันอ้างอิง (เช่น ค่าเช่าบ้าน):
         Σ  แถวใน personnel_allowances ที่ยังมีผล ณ reference_date(Y)
            AND position ของผู้รับสังกัด O
            → amount × เดือนที่นับ
         แล้วปรับด้วย buffer % จาก personnel_budget_policy
     budget_basis='manual'  → ผู้ใช้กรอกเป็นก้อน

     ** ห้ามใช้ allowance_rates มาคูณจำนวนตำแหน่ง — สิทธิ์ไม่ได้มาจากตำแหน่ง **
     ** ถ้า rate_kind='ceiling' ห้ามบวกเพดานเป็นงบ — เพดานใช้ตรวจคำขอเบิก ไม่ใช่ตั้งงบ **

รายงาน "ภาพรวมค่าใช้จ่ายบุคลากร" = สองก้อนบวกกัน  ← ที่ผู้ใช้ขอ 2026-08-10
   ** แสดงยอดย่อยแยกเสมอ อย่าโชว์แต่ยอดรวม — ไม่งั้นจะกระทบยอดกับเอกสาร พรบ. ไม่ได้ **

projected_salary(ตำแหน่ง p, ปีงบ Y):              ⭐ เพิ่ม 2026-08-10
    R = salary_raise_rounds ที่ fiscal_year=Y AND include_in_budget=1
        (ตอนนี้มีรอบเดียว = ต.ค. ปีปัจจุบัน · วันหน้าอาจมีทั้ง เม.ย.+ต.ค.)

    ถ้า  occupancy ≠ 'occupied'          → base_salary        -- อัตราว่างไม่มีคนให้เลื่อน
                                                                 ใช้อัตราแรกบรรจุของระดับ

    ถ้า  มีแถวใน personnel_assignments ที่ยังมีผล  → บังคับ estimated
         (ไปช่วยราชการ — ผลเลื่อนขึ้นกับหน่วยที่ไปช่วย ไม่ทันรอบตั้งงบ)

    ถ้า  salary_raise_progress(R, p.organization_id).status = 'completed'
         → base_salary                                       ✅ actual

    มิฉะนั้น                                                  ⚠️ estimated
         pct = salary_increment_policy(Y, p.employee_category).max_percent
         → MIN( base_salary × (1 + pct/100),
                salary_scales(p.employee_category, p.level_code).max_amount )
                ↑ ** เพดานขั้นสูง — ลืมแล้วงบสูงเกินจริงเฉพาะกลุ่มอาวุโส **

    ** ห้ามอนุมาน completed/pending จาก organizations.region **
    ** 3% ใช้เต็มทุกคน ไม่ใช่ค่าเฉลี่ย (ยืนยัน 2026-08-10) **

rate(a, p):
    r = allowance_rates(a, level ของ p, line ของ p, ณ วันอ้างอิง)
    ถ้าไม่มี r                    → 0            (ไม่มีแถว = ไม่มีสิทธิ์)
    ถ้า r.derives_from_type_id:                   ⭐ ค่าตอบแทนนอกเหนือจากเงินเดือน
          x = rate(r.derives_from_type_id, p)     -- เรียกซ้ำได้ แต่ห้ามวน
          → x                     ถ้า x > 0
          → r.fallback_amount     ถ้า fallback ไม่เป็น NULL   (มีแค่ ชำนาญการพิเศษ = 3,500)
          → 0                     ถ้า fallback เป็น NULL
    ถ้า r.percent                → base_salary × r.percent
    มิฉะนั้น                     → r.amount
```

`vacancy_rule` อ่านจาก `vacancy_recruitment` — เกณฑ์เปลี่ยนตามมติ/หนังสือเวียนแต่ละปี

### สะพานเข้าโครงเดิม — positions *ผลิต* budget_line_items ไม่ใช่ *แทนที่*

```
positions + position_versions + allowance_*
        │
        │  คำนวณ แล้ว group by (expense_item_id, organization_id, fiscal_year)
        ▼
budget_line_items          ← โครงสร้างเดิม ไม่ต้องแก้ ไม่ต้อง migrate ข้อมูลเก่า
  + source ENUM('manual','computed') DEFAULT 'manual'   ⭐ คอลัมน์เดียวที่เพิ่ม
        │
        └─ ถ้า source='computed' → คลิกดูที่มาถึงรายตำแหน่งได้
```

**ทำไมออกแบบแบบนี้:**

| | ผล |
|---|---|
| ไม่แตะ `budget_line_items` เดิม | ปีที่ยังไม่มีข้อมูลอัตรากำลัง ยังพิมพ์มือได้เหมือนเดิม |
| frontend ไม่ต้องแก้ | หน้าจอที่มีอยู่อ่าน `budget_line_items` เหมือนเดิมทุกประการ |
| เพิ่มทีละหน่วยงาน | หน่วยที่ป้อนอัตรากำลังครบ → `computed` · หน่วยที่ยังไม่พร้อม → `manual` |
| ตรวจสอบได้ | รัน computed คู่กับ manual ปีแรก แล้วเทียบผลต่างก่อนตัดสวิตช์ |

**ห้าม** ให้ `positions` เป็นแหล่งความจริงของยอดงบโดยตรง — ยอดที่ผ่านการอนุมัติแล้วต้องนิ่ง
แม้ข้อมูลอัตรากำลังจะถูกแก้ย้อนหลัง (`budget_line_items` ทำหน้าที่นี้อยู่แล้ว)
